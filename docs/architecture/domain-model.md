# 领域模型与持久化

FlowTrace 使用 TypeORM 管理 PostgreSQL 数据库，数据库结构只通过迁移演进，
运行环境禁用 `synchronize`。PostgreSQL baseline 表示当前完整结构，后续版本
只追加真实执行过的 PostgreSQL schema migration。当前 schema 将可变的当前
状态与不可变的历史事实分开保存。

## 聚合边界

- 项目节奏是全局可维护的创建模板。新建项目时复制所选节奏的环节，之后项目
  与节奏互不联动，因此节奏的增删改不会改写既有项目。
- 项目拥有版本和需求阶段模板。模板以快照形式复制到新需求，不与旧需求
  保持动态关联。
- 需求拥有阶段和 Bug。阶段是可调整的实际流程，Bug 始终作为独立子项。
- 每个阶段还保存一个稳定的工作分类：产品与需求、方案与设计、研发执行、
  联调与验证、发布交付或其他。分类创建时可按名称推断，但之后独立维护，
  用于跨不同流程模板聚焦同类工作；阶段名称不必被强行统一。
- 人员是全局负责人目录，通过稳定 ID 被需求、阶段和 Bug 引用。项目模板只
  定义流程结构；需求创建后再为每个实际阶段独立分配负责人。需求负责人只
  表示整体协调者，不替代阶段和 Bug 的负责人。
- 依赖可以连接需求、阶段或 Bug，允许跨项目，并通过 `active` 标识解除而非
  无痕删除。

## 历史事实

状态历史、排期历史、版本迁移历史和统一变更事件使用独立表保存。业务服务
修改当前字段时必须在同一事务中追加相应历史：

- `status_history` 支持补录生效时间，并据此重算实际开始、结束和各状态时长。
- `schedule_history` 保留每次计划前后值；首次正式计划同时形成基准计划。
- `version_history` 保留需求在 Backlog 和各版本之间的迁移。
- `change_events` 为按时间增量查询提供稳定事件流，也保留写入来源和 Agent。

## 数据库选择

FlowTrace 以 PostgreSQL 作为唯一受支持的数据库。JSON 快照使用 `jsonb`，时间
字段使用 `timestamptz`，内部实体标识使用 UUID。部署方可以使用 Compose 自带
的 PostgreSQL，也可以通过连接参数接入已有的托管或企业数据库。
