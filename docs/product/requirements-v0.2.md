# FlowTrace — 内部研发项目进度管理工具 MVP 产品需求规格

> 项目名：FlowTrace  
> 版本：v0.2  
> 定位：公司内部、自部署、轻量、AI 友好的研发项目进度管理工具  
> 目标读者：产品设计者、Coding Agent、后续开发维护人员  
> 本文只定义产品需求与业务行为，不约束具体技术栈、数据库、前端框架或部署方案。

---

## 1. 背景

当前团队使用企业微信 / 腾讯文档智能表格维护项目进度。

现有方式通常为每条记录填写：

- 事项名称
- 开始时间
- 结束时间
- 状态
- 负责人

并通过表格生成甘特图。

实际使用中存在两个主要问题。

### 1.1 把一个需求维护为一条记录时，过程不可见

例如一个需求从研发开始到上线共持续 20 天，如果只维护：

- 开始：8 月 1 日
- 结束：8 月 20 日
- 状态：已上线

那么甘特图只能看到一根持续 20 天的长条。

无法知道：

- 实际开发用了多久；
- 中间是否等待过；
- 是否发生过阻塞；
- 联调前是否空等；
- 测试后是否返工；
- Bug 修复用了多久；
- 排期经历过多少次调整。

### 1.2 把需求、研发、测试、上线等拆成多条独立记录时，关系容易丢失

如果在普通表格中拆成：

- 需求设计
- 开发
- 联调
- 测试
- Bug 修复
- 回归测试
- 上线

虽然时间轴更准确，但会产生新的问题：

- 很难知道这些记录属于同一个需求；
- 临时新增 Bug、返工、再次打样等事项后表格容易变乱；
- 容易漏掉关联；
- 无法方便折叠成一个需求查看整体进度；
- 很难表达需求之间甚至跨项目之间的依赖。

---

# 2. 产品目标

本产品的核心目标不是实现完整的 Jira、禅道、OpenProject 或通用项目管理平台。

它只解决一个问题：

> **以尽可能低的维护成本，真实记录一个研发需求从开始到完成经历了哪些工作、由谁负责、计划何时完成、实际如何推进、在哪里等待或阻塞，以及中途发生了多少返工。**

产品需要同时满足两种观察尺度。

### 2.1 管理者的整体视角

管理者应能快速回答：

- 每个需求目前进行到哪里；
- 当前谁在处理；
- 哪些需求正在等待；
- 哪些需求被阻塞；
- 哪些需求已经偏离原始排期；
- 一个需求下面还有多少 Bug 未解决；
- 某个需求为什么持续时间很长；
- 跨项目依赖目前卡在哪。

### 2.2 复盘时的历史视角

事后应能回答：

- 最初计划是什么；
- 排期被调整过几次；
- 实际从什么时候开始；
- 真正执行了多久；
- Waiting 了多久；
- Blocked 了多久；
- 经历了几轮修复、打样或验证；
- 哪些 Bug 导致了延期。

---

# 3. 非目标

MVP 明确不做以下能力：

- 用户账号体系；
- 登录与认证；
- RBAC / 权限系统；
- 企业微信登录；
- 企业微信通讯录同步；
- 企业微信通知；
- Sprint / Scrum；
- 燃尽图；
- Story Point；
- 工时填报；
- 人员工时考核；
- 成本管理；
- 绩效管理；
- Wiki；
- 文档系统；
- 测试用例管理；
- CI/CD 集成；
- Git / GitHub / GitLab 集成；
- 复杂报表平台；
- PMO / 项目集管理；
- 审批流程；
- 强制性的工作流引擎。

第一版默认部署在可信内部环境中，由项目经理或少量管理人员直接操作。

# 4. 核心设计原则

## 4.1 项目是流程模板的边界

不同项目拥有不同的研发流程。

例如：

### 云端项目

- 需求设计
- 需求评审
- 开发
- 联调
- 测试
- 上线

### 固件项目

- 需求确认
- 方案设计
- 开发
- 板上验证
- 联调
- 测试
- 发布

### 硬件项目

- 设计
- 首次打样
- 验证
- 定版

实际执行过程中可以动态增加：

- 修复 #1
- 二次打样
- 修复 #2
- 三次打样
- 再次验证

因此系统不能假设所有项目使用同一套阶段。

---

## 4.2 模板只用于创建需求，不持续约束旧需求

每个项目维护一套“需求阶段模板”。

创建新需求时：

1. 复制当前项目模板；
2. 为新需求生成对应阶段；
3. 此后这些阶段属于该需求自身。

项目模板以后发生修改时：

- 已创建的旧需求保持不变；
- 新模板只影响之后新建的需求；
- 不自动迁移历史需求。

---

## 4.3 需求创建后可以自由调整阶段

项目模板只是默认骨架，不是强制流程。

单个需求允许：

- 新增阶段；
- 删除尚未开始且没有历史数据的阶段；
- 取消已不再需要的阶段；
- 修改阶段名称；
- 调整阶段顺序；
- 增加临时返工阶段；
- 增加新的打样轮次；
- 增加新的验证阶段；
- 调整阶段间依赖。

例如模板为：

1. 方案设计
2. 开发
3. 联调
4. 测试
5. 发布

某个特殊需求可以调整为：

1. 方案设计
2. 开发
3. 第三方认证
4. 整改
5. 联调
6. 测试
7. 发布

---

# 5. 核心业务对象

产品 UI 中避免出现抽象的 “Work Item” 术语。

用户主要看到以下对象。

## 5.1 项目 Project

表示一类实际研发项目，例如：

- 云平台
- 固件
- 某块硬件板卡
- 某个独立软件产品

项目至少包含：

- 项目名称；
- 项目说明；
- 项目当前使用的需求阶段模板；
- 项目内需求列表。

---

## 5.2 人员 Person

人员只是“负责人目录”，不是用户账号。

人员具有：

- 姓名；
- 可选备注；
- 启用 / 停用状态。

人员：

- 没有账号；
- 没有密码；
- 没有权限；
- 不需要登录；
- 仅用于被选择为负责人。

任何需求、阶段或 Bug 都允许选择多个负责人。

停用人员后：

- 历史数据中的负责人关系保留；
- 新事项默认不再出现于负责人选择列表。

---

## 5.3 版本 Version

版本表示同一个长期项目中的一次计划交付。

例如：

- 晴岚设备固件 / 2.7
- 晴岚设备固件 / 2.8
- 晴岚设备固件 / 3.0
- 某硬件项目 / Rev A
- 某硬件项目 / Rev B

版本不是新的项目，也不是 Scrum Sprint。

它的用途只是：

> **把同一个长期项目里的需求按计划交付批次进行组织。**

版本至少包含：

- 名称；
- 所属项目；
- 状态；
- 可选计划开始时间；
- 可选计划发布时间；
- 可选实际发布时间；
- 可选说明。

版本状态建议为：

- 规划中；
- 进行中；
- 已发布；
- 已取消。

项目中允许存在一个特殊的“未排版本 / Backlog”视图，用于容纳尚未确定目标版本的需求。

### 版本与项目的边界

新建 Project 的判断标准：

> 工作对象或长期研发流程发生变化。

例如：

- 晴岚设备固件；
- 晴岚协作云；
- 晴岚开发板。

新建 Version 的判断标准：

> 同一个 Project 进入下一次计划交付。

例如：

- 固件 2.7；
- 固件 2.8；
- 固件 3.0。

不应为了每次发布复制一个新项目。

### 需求与版本

一个需求在 MVP 中：

- 可以没有目标版本；
- 默认最多属于一个目标版本；
- 可以从一个版本移动到另一个版本；
- 移动版本时必须保留历史。

例如：

`2.8 → 3.0`

应记录：

- 修改时间；
- 原目标版本；
- 新目标版本；
- 可选原因。

需求的稳定 ID 不应因为移动版本而变化。

### Bug 与版本

Bug 属于某个需求，但目标修复版本可以独立于父需求。

例如：

- 父需求首次交付版本：2.7
- Bug 发现版本：2.7
- Bug 目标修复版本：2.8

Bug 可以可选记录：

- 发现版本；
- 目标修复版本。

---

## 5.4 需求 Requirement

需求是项目中的主要管理单位。

例如：

- 支持设备 OTA；
- 增加新版绑定流程；
- 优化蓝牙配网；
- 新增某硬件接口。

一个需求包含：

- 标题；
- 描述；
- 所属项目；
- 可选目标版本；
- 目标版本变更历史；
- 多个负责人；
- 阶段列表；
- Bug 列表；
- 计划信息；
- 实际进度信息；
- 状态历史；
- 与其他需求或阶段之间的依赖关系。

需求整体进度主要由其内部阶段和 Bug 聚合得到。

---

## 5.5 阶段 Stage

阶段表示需求生命周期中一个可独立跟踪的工作过程。

例如：

- 需求设计；
- 评审；
- 开发；
- 联调；
- 测试；
- 首次打样；
- 修复；
- 二次打样；
- 验证；
- 上线。

阶段至少具有：

- 名称；
- 顺序；
- 一个或多个负责人；
- 当前执行状态；
- 计划开始时间；
- 计划结束时间；
- 实际状态历史；
- 实际开始时间；
- 实际结束时间；
- 可选备注；
- 可选依赖关系。

阶段允许在需求创建以后动态新增。

---

## 5.6 Bug

Bug 是需求下面的独立子项。

Bug 不应被写入普通阶段列表并与阶段混在一起。

每个 Bug 至少包含：

- 标题；
- 描述；
- 一个或多个负责人；
- 当前执行状态；
- 计划时间；
- 实际时间；
- 状态历史；
- 可选“发现于哪个阶段”；
- 可选依赖关系。

Bug 可以在任意阶段中被新增。

例如测试阶段发现：

- BUG-71：断网重连失败
- BUG-73：手机切后台异常
- BUG-78：配网偶现失败

这些 Bug 应作为独立事项跟踪。

---

# 6. 阶段与执行状态必须分离

业务阶段与执行状态是两个不同概念。

## 6.1 业务阶段

业务阶段描述：

> “现在正在做哪类工作？”

例如：

- 设计；
- 开发；
- 打样；
- 修复；
- 联调；
- 测试。

## 6.2 执行状态

执行状态描述：

> “这项工作目前处于什么执行状态？”

MVP 统一使用以下状态：

- `Not Started` / 待开始
- `In Progress` / 进行中
- `Waiting` / 等待中
- `Blocked` / 阻塞
- `Done` / 已完成
- `Canceled` / 已取消

所有阶段和 Bug 都使用这一组执行状态。

---

# 7. Waiting 与 Blocked 的定义

Waiting 和 Blocked 必须区分。

## 7.1 Waiting

表示：

> 当前没有主动推进，但等待的是正常、明确、预计能够满足的条件。

例如：

- 等 PCB 样板回来；
- 等测试排期；
- 等客户提供测试账号；
- 等另一个接口部署；
- 等采购到货。

Waiting 最好允许填写：

- 等待原因；
- 可选预计恢复时间；
- 可选依赖对象。

---

## 7.2 Blocked

表示：

> 当前无法继续推进，并且恢复条件或解决时间暂不明确。

例如：

- 芯片存在未定位死机；
- 技术方案存在重大风险；
- 外部接口方案未确定；
- 需求存在无法解决的冲突；
- 硬件问题尚未定位。

Blocked 应允许填写：

- 阻塞原因；
- 可选关联对象。

---

# 8. 状态历史

系统必须保留完整状态历史。

不能只保存“当前状态”。

例如：

| 生效时间 | 状态变化 | 备注 |
|---|---|---|
| 8/01 10:00 | 待开始 → 进行中 | 开始开发 |
| 8/03 18:00 | 进行中 → 等待中 | 等待 PCB |
| 8/05 14:00 | 等待中 → 进行中 | PCB 已收到 |
| 8/06 19:00 | 进行中 → 已完成 | 完成 |

据此系统可以计算：

- 总跨度；
- 进行中时间；
- Waiting 时间；
- Blocked 时间。

状态历史用于复盘，不用于员工考勤。

---

# 9. 允许补录和修改历史时间

由于第一版主要由项目经理代为维护，系统不能假设所有状态变化都会实时录入。

修改状态时：

- 默认生效时间为当前时间；
- 允许手动修改生效时间；
- 允许补录过去发生的状态变化；
- 允许修正误填的历史时间。

例如今天才得知某任务昨天上午已经开始，可以补录：

- 状态：进行中
- 生效时间：昨天 10:00
- 备注：补录

系统不得把状态时间当作严格考勤数据。

交互上不应要求用户先判断自己在填“Actual”还是在“修正历史”，
而应按操作意图区分：

- “记录进展”追加一条真实发生的状态变化；
- 发生时间默认为现在，选择过去时间时自动标记为补记；
- “修正记录”必须从一条已有历史进入，记录修正前后的值和原因；
- 负责人分配与进展记录使用独立入口，不应因为只调整负责人而
  追加状态历史。

---

# 10. 计划时间、基准计划和实际时间

系统必须同时记录：

1. 初始计划；
2. 当前计划；
3. 排期调整历史；
4. 实际执行情况。

## 10.1 初始计划 Baseline

某个阶段首次形成正式排期后，保存为基准计划。

例如：

- 初始计划开始：8/05
- 初始计划结束：8/10

之后调整排期时，Baseline 不应被覆盖。

---

## 10.2 当前计划 Current Plan

表示项目经理当前认为合理的最新计划。

例如：

第一次：

- 8/05 → 8/10

调整后：

- 8/05 → 8/13

再次调整：

- 8/05 → 8/17

当前计划显示最后一次版本。

---

## 10.3 排期调整历史

每次修改计划时间都必须保留历史记录。

例如：

| 修改时间 | 原计划结束 | 新计划结束 | 原因 |
|---|---|---|---|
| 8/08 | 8/10 | 8/13 | 联调资源延迟 |
| 8/12 | 8/13 | 8/17 | 新增兼容性问题 |

“调整原因”可以选填，不应强制填写。

---

## 10.4 实际时间

实际开始时间默认从第一次进入 `In Progress` 得到。

实际结束时间默认从最终进入 `Done` 得到。

如果存在补录或修正，以修正后的状态历史为准。

---

# 11. 需求阶段模板

每个项目拥有自己的需求阶段模板。

模板包含：

- 默认阶段；
- 阶段默认顺序；
- 不预设负责人；需求创建后再按实际阶段分配；
- 可选计划默认值；
- 可选阶段间依赖。

模板中的依赖不是必须配置。

---

## 11.1 模板示例：固件项目

- 需求确认
- 方案设计
- 开发
- 板上验证
- 联调
- 测试
- 发布

---

## 11.2 模板示例：云端项目

- 需求设计
- 需求评审
- 开发
- 联调
- 测试
- 上线

---

## 11.3 模板示例：硬件项目

- 设计
- 首次打样
- 验证
- 定版

发生返工时，可以在具体需求中动态增加：

- 修复 #1
- 二次打样
- 再次验证
- 修复 #2
- 三次打样

系统不能要求模板预先写死所有可能发生的返工轮次。

---

# 12. 依赖关系

依赖关系是本系统的重要能力，但必须符合真实研发流程，而不是传统项目管理软件里的简单“前项完成，后项才能开始”。

## 12.1 依赖可以是可选的

阶段和需求不需要强制建立依赖。

没有依赖关系时，系统仍可正常工作。

---

## 12.2 支持同项目依赖

例如：

- 联调依赖开发；
- 测试依赖联调；
- 回归测试依赖某个 Bug 修复。

---

## 12.3 支持跨项目依赖

允许一个项目中的需求或阶段依赖另一个项目中的需求或阶段。

例如：

### 硬件项目

`PCB 首次打样`

完成后：

### 固件项目

`板上验证`

即可开始。

不需要等整个硬件需求“已定版”。

---

## 12.4 依赖应尽量指向具体阶段，而不是整个需求

优先表达：

> 固件验证依赖“PCB 首次打样”完成。

而不是：

> 固件需求依赖硬件需求完成。

只有确实需要等待整个需求完成时，才建立需求级依赖。

---

## 12.5 依赖默认只提示，不强制阻止操作

现实研发中经常存在提前并行推进。

因此当某个前置依赖尚未满足时：

- 系统应提示依赖尚未满足；
- 可以显示 Warning；
- 但不得禁止用户把后续阶段改成进行中。

项目经理可以根据实际情况提前启动工作。

---

## 12.6 允许复杂交叉协作

系统不能假设两个项目之间只有单向依赖。

例如 PCB 与固件可能经历：

1. PCB 首次打样完成；
2. 固件开始板上验证；
3. 固件发现硬件问题；
4. PCB 进行修复；
5. PCB 二次打样；
6. 固件再次验证；
7. 联调再次发现问题；
8. PCB 再次修改。

产品上应允许随着真实过程动态增加阶段，并在具体阶段之间建立新的关联。

例如：

`PCB 首次打样`
→ `固件首次验证`
→ `PCB 修复 #1`
→ `PCB 二次打样`
→ `固件再次验证`

不要求用户在需求创建时预测所有返工。

---

## 12.7 不把“互相依赖”强行禁止

在需求级别上，两个项目可能看起来存在双向依赖。

例如：

- 固件依赖 PCB 提供样板；
- PCB 后续修改又依赖固件验证结果。

系统不能简单以“存在环”为理由禁止这种关系。

如果系统检测到真正无法推进的循环关系，可以提示风险，但不应强制阻止保存。

---

# 13. Bug 管理

Bug 必须是需求下的独立对象。

## 13.1 Bug 可以随时新增

例如测试过程中发现三个问题，可以直接新增三个 Bug。

不需要事先在项目模板中预留 Bug 行。

---

## 13.2 Bug 可以展开和折叠

需求视图默认允许将 Bug 聚合显示。

折叠状态示例：

`Bug 修复：3 / 5 已完成`

展开后：

- ✓ BUG-71 断网重连失败
- ✓ BUG-73 手机切后台异常
- ✓ BUG-74 极端情况下超时
- ● BUG-78 配网偶现失败
- ○ BUG-81 Android 兼容问题

---

## 13.3 Bug 总进度

MVP 采用简单的数量聚合：

`已完成 Bug 数 / 总 Bug 数`

例如：

`3 / 5，60%`

不需要为不同 Bug 设置权重。

---

## 13.4 Bug 与阶段的关系

Bug 可以可选记录：

> 发现于哪个阶段。

例如：

- 发现于：测试；
- 发现于：联调；
- 发现于：板上验证。

Bug 解决以后，可以由项目经理：

- 继续原测试阶段；
- 新增回归测试阶段；
- 新增再次验证阶段。

系统不强制某一种固定处理方式。

---

# 14. 删除、取消与历史保留

为了保证复盘数据可靠：

## 14.1 尚未产生历史的数据可以删除

例如：

- 刚创建但尚未开始的阶段；
- 误创建且没有任何历史的 Bug。

可以直接删除。

## 14.2 已经发生过实际工作的事项原则上不应物理删除

如果已经存在：

- 状态历史；
- 实际时间；
- 依赖关系；
- 排期调整记录；

则优先使用：

`Canceled / 已取消`

保留历史。

---

# 15. 需求整体状态与健康度

需求本身不需要复制一套复杂的“设计中 / 开发中 / 测试中”状态机。

需求整体显示两个维度。

## 15.1 生命周期状态

建议只显示：

- 待开始；
- 进行中；
- 已完成；
- 已取消。

## 15.2 健康提示

根据内部阶段和 Bug 聚合：

- 正常；
- Waiting；
- Blocked。

例如：

`进行中 · Blocked`

表示需求整体仍在推进，但内部存在阻塞事项。

如果同时存在多个状态，Blocked 优先展示。

---

# 16. MVP 页面

第一版只需要少量页面。

## 16.1 项目列表

显示：

- 项目名称；
- 未完成需求数；
- Waiting 数量；
- Blocked 数量；
- 最近更新时间。

支持：

- 新建项目；
- 编辑项目；
- 进入项目详情。

---

## 16.2 项目设置 / 模板页面

允许维护：

- 项目名称；
- 项目说明；
- 项目阶段模板；
- 阶段默认顺序；
- 可选阶段依赖。

模板修改只影响之后新建的需求。

---

## 16.3 项目需求列表

这是日常最主要的页面。

每个需求作为一行，可以展开。

折叠时示例：

`REQ-023 设备配网流程优化 | 进行中 | Blocked | Bug 3/5 | 8/01 → 8/25`

展开：

- 需求设计
- 开发
- 联调
- 测试
- Bug 修复 3/5
  - BUG-71
  - BUG-73
  - BUG-78
- 回归测试
- 上线

支持按以下条件过滤：

- 负责人；
- 状态；
- Waiting；
- Blocked；
- 是否延期。

MVP 不要求复杂的高级查询语言。

---

# 17. 需求详情页

需求详情页至少包括以下内容。

## 17.1 基本信息

- 标题；
- 描述；
- 所属项目；
- 负责人；
- 生命周期状态；
- 健康状态；
- 初始计划；
- 当前计划；
- 实际时间。

## 17.2 阶段

显示全部阶段。

每个阶段可编辑：

- 名称；
- 负责人；
- 状态；
- 计划开始；
- 计划结束；
- 实际状态变化；
- Waiting 原因；
- Blocked 原因。

支持新增阶段。

## 17.3 Bug

显示：

- Bug 数量；
- 完成数量；
- 当前未完成 Bug；
- 展开后的所有 Bug。

支持快速新增 Bug。

## 17.4 依赖

分为：

- 本需求依赖什么；
- 哪些需求依赖本需求；
- 具体阶段依赖。

跨项目依赖必须明确显示对方所属项目。

## 17.5 历史

至少显示：

- 状态变化；
- 排期调整；
- 阶段新增；
- 阶段取消；
- Bug 新增；
- Bug 完成。

由于 MVP 无用户系统，不要求显示操作者身份。

---

# 18. 甘特图 / Timeline

甘特图是 MVP 核心能力。

## 18.1 层级展示

甘特图按需求分组。

示例：

- REQ-023 设备配网流程优化
  - 需求设计
  - 开发
  - 联调
  - 测试
  - Bug 修复
    - BUG-71
    - BUG-73
    - BUG-78
  - 回归测试
  - 上线

需求和 Bug 组可以折叠。

需求折叠时应优先用分段汇总条表达下级阶段，而不是只画一根从
最早需求评审延伸到最晚发布的实心长条。

时间线还应提供与“初始计划 / 当前计划 / 实际过程”正交的
阶段聚焦：

- 可选阶段来自当前项目、当前筛选结果中真实存在的阶段名称；
- 允许单选或多选，需求的折叠汇总区间只由命中的阶段重算；
- 没有任何命中阶段的需求不显示，界面同时告知当前显示数量；
- Bug 是独立事项，通过“同时包含 Bug”显式控制，不伪装成一个阶段。

---

## 18.2 计划与实际

甘特图至少能区分：

- 当前计划；
- 实际执行。

最好还能查看：

- Baseline；
- Current Plan；
- Actual。

MVP 可以采用切换方式，而不要求三者始终叠加显示。

---

## 18.3 展示 Waiting 与 Blocked

实际时间轴不能只画一根实心长条。

如果阶段经历：

- 进行中；
- Waiting；
- 进行中；
- Blocked；
- 进行中；
- Done；

应能在详情或时间轴中看出这些区间。

具体视觉样式由开发实现决定，但必须能够区分：

- 实际工作；
- 等待；
- 阻塞。

---

## 18.4 依赖显示

同一项目内的阶段依赖可在甘特图中显示连线或其他清晰标识。

跨项目依赖不要求第一版把两个项目完整画在同一张甘特图。

至少应做到：

- 当前需求/阶段显示存在外部依赖；
- 显示外部项目名；
- 显示外部需求/阶段；
- 可以快速跳转查看。

---

## 18.5 时间线直接操作

时间线左侧名称继续用于定位到事项开始日期，并为需求、阶段和 Bug 提供明确的
计划编辑入口。右侧日期区域支持按住空白处横向平移。

在“当前计划”口径下，阶段和 Bug 的计划条支持：

- 拖动整条，保持工期不变并移动开始、结束日期；
- 拖动左端，只调整开始日期；
- 拖动右端，只调整结束日期。

版本和需求时间条是下级事项的汇总结果，不直接拖动，以免产生汇总时间与具体
事项相互矛盾的排期。Baseline 是只读基准，Actual 来自状态历史，也不允许直接
拖动。

拖动过程中只显示预览。松手后必须打开计划调整窗口，展示新日期并允许人工再次
修改；只有确认保存后才调用正常排期接口并追加排期历史，取消不应产生写入。
触摸设备保留计划编辑入口，不启用容易与页面滚动冲突的直接拖动。

---

# 19. 排期偏差

系统应能计算并显示简单的排期偏差。

至少包括：

- 当前计划相对 Baseline 推迟多少；
- 实际完成时间相对 Baseline 推迟多少；
- 实际完成时间相对 Current Plan 提前或推迟多少。

例如：

- Baseline：8/10
- Current Plan：8/17
- Actual：8/16

系统应能够同时体现：

- 相对原计划晚 6 天；
- 相对当前计划提前 1 天。

不能只显示“提前 1 天”。

---

# 20. 人员视角

虽然 MVP 不存在用户账号，但需要支持按人员查看负责事项。

至少支持：

- 在项目需求列表中筛选负责人；
- 查看某人当前负责的阶段；
- 查看某人当前负责的 Bug；
- 同一事项允许多个负责人。

MVP 不做：

- 个人工作台；
- 负载均衡；
- 工时统计；
- 人效分析。

---

# 21. 匿名操作模式

第一版系统没有账号。

因此：

- 打开系统即可访问；
- 打开系统即可编辑；
- 所有操作视为内部可信操作；
- 不记录操作者身份。

但仍必须：

- 对删除操作二次确认；
- 保存业务历史时间；
- 保存状态历史；
- 保存排期变更历史。

“匿名操作”不意味着可以覆盖历史记录。

---

# 22. 推荐的日常操作流程

## 22.1 创建项目

1. 新建项目；
2. 配置项目阶段模板；
3. 配置人员名单；
4. 可选配置默认阶段依赖。

## 22.2 创建版本与需求

版本可以按实际发布计划创建，例如 2.7、2.8、3.0。

创建需求时：

1. 新建需求；
2. 可选指定目标版本，未确定时放入 Backlog；
3. 自动复制当前项目模板；
4. 根据实际需求删减或增加阶段；
5. 分配负责人；
6. 填写计划时间。

需求后续允许在版本之间移动，并保留迁移历史。

## 22.3 推进需求

项目经理根据实际情况更新：

- 状态；
- 负责人；
- 实际发生时间；
- Waiting；
- Blocked；
- 排期。

允许补录。

## 22.4 发现 Bug

直接在需求下新增 Bug。

Bug 自动进入该需求的 Bug 分组。

## 22.5 发生返工

不要把所有历史压回原来的单一状态。

根据实际过程：

- 新增修复阶段；
- 新增打样阶段；
- 新增回归阶段；
- 或新增 Bug。

使时间轴能够真实反映返工。

## 22.6 跨项目协作

在具体阶段之间建立依赖或关联。

例如：

`硬件 / 首次打样`
→
`固件 / 板上验证`

如果后续硬件再次修改，再新增：

`固件 / 首次验证`
→
`硬件 / 修复 #1`
→
`硬件 / 二次打样`
→
`固件 / 再次验证`

---

# 23. MVP 必须满足的关键场景

## 场景 A：普通软件需求

一个需求经历：

- 设计；
- 开发；
- 联调；
- 测试；
- 上线。

系统能清楚显示每个阶段计划与实际时间。

---

## 场景 B：开发中存在等待

开发过程：

- 开发 2 天；
- 等待联调环境 2 天；
- 继续开发 1 天。

系统不能只显示“开发持续 5 天”。

必须能够看出：

- 进行中时间；
- Waiting 时间；
- Waiting 原因。

---

## 场景 C：测试发现多个 Bug

测试发现 5 个 Bug。

系统要求：

- 每个 Bug 可以独立负责人；
- 每个 Bug 独立状态；
- Bug 可以展开；
- 折叠后显示 `3 / 5`；
- Bug 修复过程保留时间历史。

---

## 场景 D：硬件反复打样

真实过程：

- 设计；
- 首次打样；
- 验证；
- 修复；
- 二次打样；
- 再次验证；
- 修复；
- 三次打样；
- 定版。

系统必须允许在执行过程中动态插入这些阶段。

---

## 场景 E：排期连续调整

初始计划：

`8/05 → 8/10`

第一次调整：

`8/05 → 8/13`

第二次调整：

`8/05 → 8/17`

实际：

`8/06 → 8/16`

系统必须保留全部历史，而不是只剩下最后一个计划。

---

## 场景 F：跨项目阶段依赖

硬件项目：

`PCB 首次打样`

完成后固件项目：

`板上验证`

即可启动。

固件项目不需要等待整个硬件需求定版。

系统必须能表达这种依赖。

---

## 场景 G：跨项目反复协作

PCB 与固件经历：

- PCB 首次打样；
- 固件验证；
- PCB 修复；
- PCB 二次打样；
- 固件再次验证。

系统必须允许这种逐步追加的交叉关系，不应因为两个项目概念上存在“互相依赖”而拒绝建立。

---

# 24. MVP 验收标准

只有同时满足以下条件，MVP 才算达到可用状态。

## 24.1 项目与模板

- [ ] 可以创建多个项目。
- [ ] 每个项目拥有独立需求阶段模板。
- [ ] 修改模板不会修改已有需求。
- [ ] 新建需求时复制当前模板。
- [ ] 单个需求可以自由修改自己的阶段。

## 24.2 人员

- [ ] 有独立人员名单。
- [ ] 人员不是账号。
- [ ] 一个事项可以选择多个负责人。
- [ ] 可以按负责人筛选事项。

## 24.3 版本

- [ ] 一个项目可以包含多个版本。
- [ ] 需求可以不属于任何版本。
- [ ] 一个需求默认最多有一个目标版本。
- [ ] 需求可以在版本之间移动。
- [ ] 移动版本保留历史。
- [ ] 需求 ID 不因版本变化而变化。
- [ ] Bug 可以拥有独立的目标修复版本。
- [ ] 可以按版本筛选需求和甘特图。

## 24.4 状态

- [ ] 阶段和 Bug 使用统一执行状态。
- [ ] Waiting 与 Blocked 分开。
- [ ] Waiting / Blocked 可以填写原因。
- [ ] 完整保存状态历史。
- [ ] 状态变化允许补录过去时间。

## 24.5 排期

- [ ] 支持计划开始和结束。
- [ ] 保留 Baseline。
- [ ] 显示 Current Plan。
- [ ] 保存每次排期修改历史。
- [ ] 保存实际开始和实际结束。
- [ ] 能看出相对原始计划和当前计划的偏差。

## 24.6 Bug

- [ ] 可以随时给需求新增 Bug。
- [ ] Bug 是独立可跟踪对象。
- [ ] Bug 有独立负责人、状态和时间。
- [ ] Bug 可以折叠成总进度。
- [ ] Bug 可以展开查看明细。

## 24.7 依赖

- [ ] 同项目需求/阶段之间可以建立依赖。
- [ ] 跨项目可以建立依赖。
- [ ] 可以依赖具体阶段，而不只是整个需求。
- [ ] 未满足依赖时系统提示，但不强制禁止推进。
- [ ] 不简单禁止概念上的双向跨项目协作。

## 24.8 甘特图

- [ ] 按需求展示层级。
- [ ] 需求可以折叠。
- [ ] 阶段可以展示计划时间。
- [ ] 阶段可以展示实际时间。
- [ ] Waiting 与 Blocked 的时间可以被识别。
- [ ] Bug 可以作为需求下的子项展开。
- [ ] 同项目依赖可以被直观看到。
- [ ] 跨项目依赖至少有清晰入口。

## 24.9 历史与复盘

- [ ] 能查看一个事项所有状态变化。
- [ ] 能查看全部排期调整。
- [ ] 能计算 Waiting 时间。
- [ ] 能计算 Blocked 时间。
- [ ] 能看到需求经历过的返工阶段。
- [ ] 已经有历史数据的事项不能被轻易无痕删除。

## 24.10 AI 与机器接口

- [ ] 核心业务能力具有结构化 HTTP API。
- [ ] 提供 OpenAPI 描述。
- [ ] 提供第一方 MCP Server。
- [ ] MCP 复用与 Web UI 相同的业务规则。
- [ ] 重要对象具有稳定 ID。
- [ ] 提供项目 / 版本结构化 Snapshot。
- [ ] 支持按时间查询 Changes Since。
- [ ] AI 写入保留来源。
- [ ] AI 修改状态、排期、版本时不会绕过历史记录。
- [ ] 一个仅获得 MCP 接口的 Agent 能完成第 27.10 节的验收场景。

# 25. MVP 产品边界

如果某项需求不能直接帮助回答以下问题，应优先推迟：

> “这个需求目前到底做到哪里了？”

> “谁正在负责？”

> “为什么还没完成？”

> “是在工作、正常等待，还是被阻塞？”

> “原来计划什么时候完成？后来为什么调整？”

> “测试后又返工了多少次？”

> “有哪些 Bug 还没解决？”

> “它正在等另一个项目的哪个具体阶段？”

MVP 的目标是把这些问题解决得比“腾讯文档智能表格 + 甘特图”明显更自然。

不要在第一版把产品扩展成通用项目管理平台。

---

# 26. 后续可能扩展，但不属于 MVP

以下能力应确保未来可扩展，但第一版不实现：

- 用户账号；
- 企业微信 SSO；
- 企业微信通讯录同步；
- 企业微信机器人提醒；
- 操作者审计；
- 评论；
- @成员；
- 附件；
- 全局搜索；
- 跨项目总时间轴；
- 项目仪表盘；
- 项目风险看板；
- Git / PR / Commit 关联；
- 自动从 Bug 创建修复阶段；
- 自动排期；
- 依赖变更提醒；
- 里程碑；
- 项目版本 / Release；
- 更复杂的统计和复盘报表。

这些能力不应提前污染 MVP 的核心数据和交互。

---


# 27. AI First / Machine Interface

AI 友好属于 MVP 的核心要求，不是后续附加功能。

产品的目标是让一个不了解内部实现的 AI Agent 能够：

- 读取项目状态；
- 总结版本进展；
- 找出 Waiting / Blocked / 延期事项；
- 查询某个需求为什么没有完成；
- 创建需求；
- 更新阶段状态；
- 补录历史时间；
- 创建 Bug；
- 调整排期；
- 修改目标版本；
- 创建跨项目依赖；
- 总结某个时间点之后发生的变化。

AI 集成不能依赖网页自动化、浏览器点击或直接访问数据库。

---

## 27.1 API-first

所有核心业务能力必须通过稳定、结构化的机器接口暴露。

原则：

> **Web UI 能完成的核心业务操作，机器 API 也必须能完成。**

至少覆盖：

- 项目；
- 版本；
- 需求；
- 阶段；
- Bug；
- 人员；
- 状态历史；
- 排期历史；
- 版本迁移历史；
- 依赖关系。

MVP 应提供完整的 HTTP API，并提供可供机器理解的 OpenAPI 描述。

具体 REST 路径、HTTP 方法和技术实现由开发阶段决定，本 PRD 不强制规定。

业务逻辑应集中在统一的 Domain Service / Application Service 中。

Web UI、HTTP API 和 MCP 不得各自实现一套不同的业务规则。

---

## 27.2 MCP Server

MVP 应提供第一方 MCP Server，作为 AI Agent 的主要接入方式之一。

MCP Server 应调用与 Web UI 相同的业务能力，不应：

- 直接操作数据库；
- 绕过业务校验；
- 维护另一套状态机；
- 暴露内部表结构作为主要操作方式。

MCP Tool 应采用业务语义，而不是数据库 CRUD 语义。

推荐的 Tool 粒度示例：

- `list_projects`
- `list_versions`
- `get_project_snapshot`
- `get_version_snapshot`
- `get_requirement`
- `create_requirement`
- `move_requirement_to_version`
- `update_stage_status`
- `add_stage`
- `report_bug`
- `update_bug_status`
- `reschedule_stage`
- `add_dependency`
- `get_changes_since`

具体 Tool 名称允许开发阶段调整，但语义必须保持清晰。

不推荐仅提供：

- `create_item`
- `update_item`
- `set_field`
- `create_relation`

这类要求 AI 理解内部数据库模型的低层接口。

---

## 27.3 稳定 ID

所有需要被人或 AI 引用的重要对象必须具有稳定、唯一、可读的 ID。

例如：

- 项目：`FW`
- 需求：`FW-128`
- Bug：`FW-BUG-231`

要求：

- ID 创建后保持稳定；
- 修改标题不改变 ID；
- 移动版本不改变 ID；
- AI 可以通过 ID 精确引用对象；
- 同名或相似标题不能造成歧义。

ID 不应包含目标版本号。

不推荐：

`FW-2.8-128`

因为需求可能从 2.8 延期到 3.0，而身份不应变化。

---

## 27.4 Project / Version Snapshot

系统必须提供适合 AI 一次性读取的结构化快照。

AI 不应为了回答：

> “晴岚设备固件 2.8 现在怎么样？”

而执行几十次逐项查询。

至少应支持：

- 项目快照；
- 版本快照。

快照应以结构化数据返回事实，不直接依赖 LLM 生成总结。

版本快照至少应能包含：

- 版本基本信息；
- 计划发布日期；
- 需求总数；
- 已完成数量；
- 进行中数量；
- Waiting 数量；
- Blocked 数量；
- 延期数量；
- 未完成 Bug 数量；
- 当前主要 Waiting；
- 当前主要 Blocked；
- 外部依赖；
- 最近变化。

AI 在此结构化事实基础上生成自然语言总结。

---

## 27.5 Changes Since

系统必须支持按时间获取增量变化。

例如：

`获取 2026-08-23 09:00 之后发生的所有变化`

至少包括：

- 状态变化；
- 新增需求；
- 新增 Bug；
- Bug 完成；
- 排期调整；
- 目标版本变化；
- 新增或解除依赖；
- 新增或取消阶段；
- Waiting / Blocked 的进入与解除。

该能力主要用于：

- 每日项目摘要；
- 周报；
- 会议前回顾；
- AI 自动识别重要变化。

AI 不应每次为了获取“昨天发生了什么”重新扫描整个项目。

---

## 27.6 AI 写入来源

虽然 MVP 没有用户系统，但所有业务变更必须保留一个轻量来源字段。

至少区分：

- `manual`
- `api`
- `agent`

对于 Agent 写入，建议额外记录：

- Agent 名称或调用方标识；
- 修改时间；
- 修改原因或上下文（如果有）。

例如：

- 来源：Agent
- Agent：PM Assistant
- 修改：计划结束 8/27 → 8/30
- 原因：根据 8/24 项目例会调整

这不是员工审计或考勤功能，而是用于回答：

> “这项数据为什么变成这样？”

人工匿名操作只需要记录：

`source = manual`

不要求识别具体人员。

---

## 27.7 AI 写操作必须复用正常业务规则

AI 进行以下操作时：

- 修改状态；
- 补录状态时间；
- 修改排期；
- 移动版本；
- 新增 Bug；
- 新增依赖；

必须产生与人工操作完全相同的：

- 状态历史；
- 排期历史；
- 版本变更历史；
- 来源信息；
- 依赖数据。

AI 不允许通过某个快捷接口直接覆盖最终字段，从而绕过历史记录。

---

## 27.8 批量更新

AI 经常需要根据会议记录一次修改多个事项。

系统应支持合理的批量操作能力。

例如：

- 一个需求改为 Waiting；
- 一个需求标记 Done；
- 新增两个 Bug；
- 一个需求从 2.8 移动到 3.0；
- 一个阶段延期三天。

批量调用至少需要：

- 对每个操作分别返回成功 / 失败；
- 单项失败必须说明原因；
- 不允许静默丢失部分修改。

`preview / dry-run` 属于推荐能力。

如果实现成本合理，应允许 AI 在真正写入之前获得：

> 即将执行哪些修改。

但 dry-run 不作为 MVP 硬性验收条件。

---

## 27.9 结构化输出优先

面向 AI 的主要读取接口应优先返回结构化数据，而不是只有 Markdown 或自然语言。

例如查询需求时，应返回明确字段：

- ID；
- 项目；
- 版本；
- 当前状态；
- 健康状态；
- 当前阶段；
- 负责人；
- Bug；
- Waiting；
- Blocked；
- 依赖；
- Baseline；
- Current Plan；
- Actual。

AI 再自行决定如何总结。

---

## 27.10 AI MVP 验收场景

将系统交给一个不了解内部实现、只获得 MCP 接口的 Agent。

Agent 必须能够正确完成以下任务：

### 查询

- [ ] “有哪些项目？”
- [ ] “晴岚设备固件有哪些版本？”
- [ ] “2.8 当前进展怎么样？重点告诉我延期、Waiting 和 Blocked。”
- [ ] “FW-128 为什么还没完成？”
- [ ] “有哪些事项正在等待其他项目？”
- [ ] “从昨天上午 9 点以来发生了哪些变化？”

### 写入

- [ ] “给 FW-128 新增一个 Bug：二次配网可能失败，负责人张三，发现于测试阶段。”
- [ ] “这个 Bug 实际昨天已经开始修，补录一下。”
- [ ] “把 FW-128 的板上验证计划从 25 日调整到 28 日，并记录原因。”
- [ ] “把 FW-142 从 2.8 移到 3.0，并记录延期原因。”
- [ ] “让固件板上验证依赖硬件项目的 PCB 首次打样阶段。”

执行上述操作后：

- [ ] Web UI 能立即看到相同结果；
- [ ] 状态历史正确；
- [ ] 排期历史正确；
- [ ] 版本迁移历史正确；
- [ ] 来源被记录为 Agent；
- [ ] AI 无需理解数据库结构。

---

# 28. 最终产品原则


本工具不是用来强迫团队遵循某种项目管理方法论。

它的目的只是：

> **把已经真实发生的研发过程准确、低成本地记录下来，并让管理者能从“需求整体”一直展开到“具体返工、Bug、等待和阻塞”。**

系统应优先适应现实研发过程，而不是要求现实研发过程适应系统。

特别是：

- 可以并行；
- 可以提前启动；
- 可以返工；
- 可以反复打样；
- 可以跨项目互相协作；
- 可以漏填后补；
- 可以调整排期；
- 可以临时增加 Bug；
- 可以临时增加阶段。

这些都应被视为正常研发行为，而不是异常流程。
