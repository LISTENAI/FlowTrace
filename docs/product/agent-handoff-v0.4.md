# Agent 交底与来源审计增量

## 目标

不同 Agent 会话接手同一项目时，需要获得一份可持续维护的项目交底，避免只靠
单次对话记忆重新理解项目。同时，所有审计界面都应能区分人工、API 与 Agent
操作，并在 Agent 自己能够准确获知时记录其模型标识与版本。

## Agent 交底

- 每个 Project 只有一份当前交底，内容使用 Markdown。
- 交底与面向成员的 Project `description` 完全独立。
- 交底记录长期有效的项目背景、术语、工作约定、关键决策、未决问题和接手建议。
- 状态、负责人、排期、依赖和过程历史仍以结构化数据为准，不应复制进交底。
- 交底不能覆盖系统安全、权限或 FlowTrace 业务规则。
- 每次保存都生成单调递增的不可变修订，并记录来源、调用方、可选模型和原因。
- 更新必须携带读取到的当前修订号；发生并发变化时拒绝覆盖，要求重新读取。
- 人工可在项目设置中查看和编辑；Agent 通过 HTTP API 与 MCP 读取、维护和追溯。
- 项目与版本 Snapshot 返回当前交底，使新会话获取整体状态时同时完成接手。

## Agent 模型审计

现有 `source` 与 `agentName` 含义保持不变：

- `source` 区分 `manual`、`api` 与 `agent`。
- `agentName` 标识执行操作的 Harness、机器人或调用方。
- `agentModel` 是 Agent 自报的精确模型标识与版本，例如
  `openai/gpt-5.6-sol`。

`agentModel` 不是身份认证信息，也不由服务端猜测。运行时无法准确提供时必须
留空。状态、排期、版本迁移、依赖、变化事件和 Agent 交底修订均保留该字段。
Web 审计界面应展示来源，并在来源为 Agent 时展示已记录的调用方与模型。

## MCP 行为

- 首次对某项目开展实质工作时读取 Snapshot 中的交底，或调用
  `get_project_handoff`。
- 只有用户授权的项目维护产生了后续会话确实需要的稳定信息时，才维护交底。
- 只读请求、临时推理、聊天全文、个人偏好和秘密不得写入交底。
- `update_project_handoff` 提交完整最新内容、当前修订号、调用方、可选模型和
  具体原因。
- 修订冲突时重新读取并有意识地合并，不允许盲目覆盖。

## 关联结构调整

取消旧阶段、重接依赖或一次执行三项以上关联修改时，MCP 应先预演完整计划，
向用户展示业务对象级差异，再在确认后原子应用同一计划。不得用一串可能部分
成功的单项写入模拟事务。

- 新结构和替代关系先建立，旧阶段、旧需求和旧依赖最后停用。
- 旧阶段明确被拆分或合并到新阶段时，应记录接替关系，而不是留下无法解释的
  单独取消记录；旧阶段的历史不复制到新阶段。
- 计划内新建对象使用操作名供后续步骤引用，不由 Agent 构造临时 UUID。
- 依赖只记录用户明示或权威来源能够支持的事实；合理猜测只能作为建议。
- 应用前若项目已变化，原确认失效，必须重新读取和预演。
- 应用后以实际变化事件和对账结果核验，不以 Agent 自己的操作清单代替事实。
- 结构调整形成的长期术语、边界和未决问题应更新项目交底；当前状态、排期和
  依赖仍只保存在结构化字段中。
